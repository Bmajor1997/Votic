## Firebase key restrictions: instructions only

The app initializes `@firebase/app` and `@firebase/auth` (JavaScript SDK), and the APK workflow supplies a **web** Firebase app ID (`:web:`). Native Google Sign-In supplies a Google credential to that JavaScript auth flow. Therefore an Android package restriction cannot be assumed compatible with this API key merely because the app runs on Android.

1. In Google Cloud Console for the existing project, open APIs & Services → Credentials. Match each Firebase key to its actual consumers, using workflow/public config and Firebase app configuration. Do not modify a shared production key while investigating.
2. With a separate test key/build first, set API restrictions for the services actually called. For the observed authentication flow, preserve Identity Toolkit API (`identitytoolkit.googleapis.com`) and Token Service API (`securetoken.googleapis.com`). Inventory any other Firebase consumers before removing their required APIs. Do not enable unrelated paid APIs such as Generative Language for a public Firebase key.
3. For a key genuinely used by the **native Android SDK**, use Android app restrictions with `com.votic.app` and the relevant installed-app SHA-1: Play App Signing's app-signing certificate for Play installs, upload certificate only for APKs actually signed with it, and debug certificate only on a separate local-test key if needed. An upload certificate is not the certificate of a Play-delivered APK.
4. For browser consumers, use a separate browser key restricted to the real permitted HTTPS referrers. Do not apply those referrer rules to native JavaScript SDK traffic, which may have no browser referrer. For Votic's present React Native JavaScript auth flow, verify supported application restriction headers in a test build before imposing Android/referrer restrictions; if incompatible, retain narrowly scoped API restrictions and evaluate native SDK migration separately.
5. Test email signup/login, Google and Apple where supported, password reset, token refresh after expiry, sign-out and account deletion with the new test key. Observe blocked-service/restriction errors without logging tokens. Only then propose reviewed production restrictions for approval. Authentication tokens and backend verification, not possession of this public key, authorize Votic requests.

Sources checked: [Google Play User Data](https://support.google.com/googleplay/android-developer/answer/10144311), [prominent disclosure guidance](https://support.google.com/googleplay/android-developer/answer/11150561), [Firebase API-key guidance](https://firebase.google.com/docs/projects/api-keys). Play disclosure must be in normal app usage, describe data/purpose/sharing, and require affirmative consent where applicable; a policy link or internal-track choice is not a substitute.
